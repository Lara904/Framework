# NFR-5302 — All system batchs (job, script, Netbatch stage, etc.) can be restarted

## 1. NFR Metadata

- **ID:** NFR-5302
- **Title:** All system batchs (job, script, Netbatch stage, etc.) can be restarted
- **Primary Category:** Reliability

---

## 2. Executive Summary

- **The "Goal":** It is essential to ensure consistency of processing without loss of data and maintain integrity of results already produced, mainly in case of incident. After withdrawal, following the incident, the recovery of process should not be managed by operating techniques: they should be ensured within the program and allow a processing re-run.
- **Why it matters:** Failure to implement this NFR may result in non-compliance with Reliability standards, increased operational risk, and potential rejection during technical control gates (TCC/CTC).

---

## 3. Technical Requirements

### Key Constraints

- It is essential to ensure consistency of processing without loss of data and maintain integrity of results already produced, mainly in case of incident. 
After withdrawal, following the incident, the recovery of process should not be managed by operating techniques: they should be ensured within the program and allow a processing re-run.
- Cloud context : all application, functional or technical processes are subject to being able to restart, that goes for the integrity and coherence of the application data. You cannot admit embedding erroneous data or having unreadable content. The development teams will have to take into account a so-called recovery treatment in order to correct the problem.

Realization:
- Can use the means provided by the DBMS (Checkpoints, commits, rollbacks…) for the input and output ‘FLOWS’.
- Should, when using batch files, be able to reset without specifically manipulating the transaction files (data recycling).
- Cloud context: if you receive a file with erroneous data, the sender must be able to correct the file and return it to us (incorrect file format or header). The process can be restarted to have a built-in database and up-to-date data. Any processing must be able to be performed again to take into account anomalies. Each batch must be executed under a specific scheduler, and a template must be created into Ansible Tower.
