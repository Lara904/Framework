# NFR-5201 — The system is monitored and generate automatically incidents to the good entities

## 1. NFR Metadata

- **ID:** NFR-5201
- **Title:** The system is monitored and generate automatically incidents to the good entities
- **Primary Category:** Reliability

---

## 2. Executive Summary

- **The "Goal":** All the events, which are likely to disturb the functioning of the application, must be monitored (TP not open, batch MAJ not done, files not arrived, process absent...). The events enable to anticipate the malfunctioning, which must also be monitored (for example, database volume).
- **Why it matters:** Failure to implement this NFR may result in non-compliance with Reliability standards, increased operational risk, and potential rejection during technical control gates (TCC/CTC).

---

## 3. Technical Requirements

### Key Constraints

- For any new application or any new applicative occurrence or major evolution, the system integrator must implement the IndusGen Base.
The application monitoring (including the preventive monitoring of thresholds – data volumes and activity) was tested and is operational.
- When the elements to be monitored are not part of the standard, the request to be done is at the start of the design phase, because this implementation can involve developments in « automatisation » [automation] sector.
To set general supervision, the system integrator must use the IndusGen base script of monitoring module. The system integrator do all test in first in pre-production and secondly in production.
- On Cloud platforms (AWS, AZURE, GCP …)
- Use the native cloud monitoring tools (Cloud Watch, Azure monitoring, …)
- To manage alerts, you can trigger actions from defined threshold to send them to PSA SM.
- Only the project team knowing the criticality of each service or feature must define thresholds and alerts.
- Windows Case:
- System integrator (or CFAO support) requests the installation of OSP product to «Automatisation» [Automation] sector, by a model change (refer « OSP » web for access to formulae and model change). The monitoring parameter can be modified by the OSP menu.

Unix Case:
- The monitoring tool is part of installation of UNIX machine database (without being started). It is activated by System integrator who selects once for the entire OSP plat-form of "prod" or "test" destination, according to its requirements. This choice determines the final destination of the incidents: 
"prod": Incidents on production SDI, with possibility to redirect all or part of incidents on pre-production SDI.
"test": Incidents on pre-production SDI, without possibility to redirect on production SDI.

z/OS Case:
- All the batch processes must be run thru TWS
OI (operator instructions) must be filled.
