# NFR-8201 — The system must be designed to be installed on any environment corresponding to the defined technical architecture

## 1. NFR Metadata

- **ID:** NFR-8201
- **Title:** The system must be designed to be installed on any environment corresponding to the defined technical architecture
- **Primary Category:** Portability

---

## 2. Executive Summary

- **The "Goal":** Make the applications independent from the physical coding of terminals, machines, CPU, networks (IP address)... Thus, it ensures a better portability, independence from the enhancement of these components.
- **Why it matters:** Failure to implement this NFR may result in non-compliance with Portability standards, increased operational risk, and potential rejection during technical control gates (TCC/CTC).

---

## 3. Technical Requirements

### Key Constraints

- Use logical names (and not physical).
If necessary, handle the hardware as external configuration managed by the user (or by operations).
Characterize each application (or copy of an application) by different coding (see specific PRD and CGS concepts).
- z/OS: CGS, PRD
- UNIX: PRD occurrence
- Windows: PRD occurrence
- VMS: logical names in Group
- Tandem: system integration coding, process renaming.
- An application should not require a system configuration or technical environment that would be specific to it. 
For a given technology, the applications should use common system integration tools.
- Cloud context: always use environment variables in the code, do not put a link or something hard in the code of the application
On AWS: The reversibility is set to 3 months. So your application must be able to change its cloud in 3 months.
